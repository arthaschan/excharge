## 一、核心思路：逆向利用故障稀疏性

### 💡 关键洞察

充电站故障天然是**稀疏事件**：
- 一个充电站一年 365 天 × 1440 分钟 = 52.5 万条时序记录
- 真正故障的时段可能只有几十个小时
- 站长对「哪台设备、什么时候、为什么坏」心中有数

### 标注策略：正向获取异常 + 逆向标注正常

| 传统方式 | 本方案 |
|---------|--------|
| 逐条判断 52.5 万条记录 | **只标注「坏的」几十条** |
| 标注正常 = 全部看一遍 | **其余全部自动 = 正常** |
| 工作量巨大、易出错 | **站长一句话解决核心标注** |

**标注工作量从 52.5 万条 → 几十条（仅需标注异常部分），其余自动生成。**

```
完整时序数据（全年每分钟状态）
    │
    ├── 坏的时间点  ──→  标注为「异常」  ← 站长提供
    │
    └── 其他时间点  ──→  标注为「正常」  ← 自动生成 ✅

→ 完整标注数据集 ✅
```

### 标注数据表设计（站长提供的内容）

| 字段 | 说明 | 来源 |
|------|------|------|
| 设备编号 | 充电桩编号 | 站长提供清单 |
| 故障开始时间 | 什么时候开始坏 | 站长口述 / 运维记录 |
| 故障结束时间 | 什么时候修好 | 站长口述 / 运维记录 |
| 故障原因 | 什么故障类型 | 站长口述 / 运维记录 |
| 维修措施 | 怎么修的 | 可选 |

**⚠️ 关键前提：站长记录的时间点和时序数据的时间戳必须使用同一时区和时间基准。** 联系时需确认。

### Step 3：标注数据集自动化生成

**核心逻辑（两条腿走路）：**

```
① 标注异常（站长提供）          ② 标注正常（自动生成）
─────────────────────           ──────────────────────────────
故障记录表（手动整理）            时序数据中除异常时段外的所有时段
↓                               ↓
与时序数据对齐                   统一标注为「正常」
↓                               ↓
标注为对应故障类型               ↓
（接触不良/过温/通讯故障…）      自动获得「正常」标签 ✅
```

**最终标注数据集：**

```
设备编号  | 开始时间           | 结束时间           | 故障类型    | 标签
CB-001   | 2026-07-13 14:32  | 2026-07-13 15:10  | 接触不良    | 异常
CB-003   | 2026-05-20 09:30  | 2026-05-20 15:00  | 过温保护    | 异常
CB-005   | 2026-03-15 14:00  | 2026-03-16 10:00  | 枪头损坏    | 异常
CB-001   | 2026-07-13 15:10  | 2026-07-16 08:00  | —          | 正常 ← 自动
CB-003   | 2026-05-20 15:00  | 2026-07-02 18:00  | —          | 正常 ← 自动
CB-007   | 2026-01-01 00:00  | 2026-12-31 23:59  | —          | 正常 ← 自动
…        | …                 | …                 | —          | 正常 ← 自动
```

→ 每条时序记录现在都有标签（异常 / 正常 / 故障类型），**完整标注数据集 ✅**

**Python 伪代码（标注自动生成）：**

```python
import pandas as pd

# ① 读取时序数据（全站所有设备 × 全年时间）
ts = pd.read_csv('充电站时序数据.csv', parse_dates=['时间'])
ts['标签'] = '正常'  # 默认全部正常

# ② 读取站长提供的故障记录
faults = pd.read_csv('故障记录表.csv', parse_dates=['故障开始时间', '故障结束时间'])

# ③ 遍历每条故障记录，标注异常时段
for _, fault in faults.iterrows():
    mask = (
        (ts['设备编号'] == fault['设备编号'])
        & (ts['时间'] >= fault['故障开始时间'])
        & (ts['时间'] <= fault['故障结束时间'])
    )
    ts.loc[mask, '标签'] = '异常'
    ts.loc[mask, '故障类型'] = fault['故障原因']

# ④ 导出完整标注数据集
ts.to_csv('标注数据集.csv', index=False)
print(f"标注完成：异常={len(ts[ts['标签']=='异常'])}条，正常={len(ts[ts['标签']=='正常'])}条")
```

### Step 4：标注质量人工验证

**验证逻辑：充电站发生故障时，功率曲线应有明显异常（下降或为零）。**

```
随机抽 20% 的故障记录 → 与时序数据交叉验证
                                              │
                              ┌─ 故障时段功率显著下降 ─→ 标注验证通过 ✅
                              │
                              └─ 故障时段功率正常 ─→ 人工复核该记录 ⚠️
```

**Python 伪代码（自动质量检查）：**

```python
# 验证一条故障记录
fault_record = faults.iloc[0]
events = ts[
    (ts['设备编号'] == fault_record['设备编号'])
    & (ts['时间'] >= fault_record['故障开始时间'])
    & (ts['时间'] <= fault_record['故障结束时间'])
]

power_during_fault = events['充电功率'].mean()
power_normal = ts[
    (ts['设备编号'] == fault_record['设备编号'])
    & (ts['标签'] == '正常')
]['充电功率'].mean()

if power_during_fault < power_normal * 0.5:
    print("标注验证通过 ✅")
else:
    print("标注存疑 ⚠️ 建议人工复核")
```

**专家确认：** 邀请导师或工程师抽查 10 条故障记录，验证故障类型归类是否正确，正确率 > 85% 即可接受。

### Step 5：模型训练 + GradCAM 可解释性分析

**时序分类模型：**

- LSTM / Transformer Encoder
- 二分类（正常 vs 异常）或四分类（正常 / 接触不良 / 过温 / 通讯故障）

**GradCAM 可解释性：**

- 对每一次异常预测，GradCAM 输出「哪些时间点的哪些特征导致了判断」
- 这就是 TAIG 主题中「透明性」的落地

**评估指标：**

| 指标 | 含义 |
|------|------|
| Accuracy / F1 / AUC-ROC | 分类性能 |
| AOPC | GradCAM 质量评估 |
| 专家满意度评分 | 3~5 位工程师对 GradCAM 输出可信度打分（1~5）|

## 四、风险与对策

| 风险 | 严重程度 | 对策 |
|------|---------|------|
| 站长记录不完整（有故障但漏记） | 高 | 用时序数据中「功率骤降/为零」的时段反向验证，补充遗漏 |
| 故障时间粒度不够细（只有小时/天） | 中 | 以「天」为单位标注故障时段，不强求精确到分钟 |
| 设备编号格式在日志和时序数据中不一致 | 高 | 提前拿到编号清单后，做编号映射表 |
| 时区/时间基准不一致导致对齐失败 | 高 | 联系时明确确认时区（北京时间 / UTC） |
| 故障描述用语不统一（如"枪头坏了"vs"充电枪损坏"） | 低 | 提取后建立故障类型词典，统一归类 |
| 维修时间跨度大（故障持续多天）| 中 | 按天粒度处理，减少边界歧义 |
